# M4 wrap-up (slice 11)

## Measuring

- **Both machines measured M4 with the full script** on a release build of main after #189:
  - Windows by Claude Code;
  - the MacBook by the Mac session, at Nevada's request.
- **Every target passes on both.**
  - The Editor's sliders (PRF-6) hold every frame the display shows, on WebGPU and WebGL2, from 12 to 48 MP: 116 to 120 frames a second on Windows, and 60, WebKit's limit, on the Mac.
  - The results go in `docs/benchmarks/m4-editor.md`, after a last Windows run on a quiet computer (below).
- **Next photo in the Viewer (PRF-5) is slower on Windows:** a median of 84 to 85 ms in two full runs, against 62 ms in M3. That's within the 150 ms target, but over the 75 ms aim.
  - The Mac is unchanged, at 40 ms.
  - Claude Code found the cause by comparing two `--small` builds back to back. Since slice 4, each photo also fetches its guide image, about 6 MB, through WebView2. With the guide fetched, the median was 70 ms; with the photo reused as its own guide, 52 ms.
  - Nevada decided to record PRF-5 as it is and fix it later, in M5 or in M7's performance audit (#190).
- **Other work on the PC affects the numbers.** Nevada pointed out that they were using the Windows computer during the runs. That fits the first scan (PRF-3), which uses every core: 104 and 112 a second, against 133 in M3. It also fits the slowest search letter going from 124 ms to 173 ms between runs.
  - The final Windows run waited until the computer was quiet. Nevada left it mostly idle, with only a video playing, a few percent of the CPU. The results are in `docs/benchmarks/m4-editor.md`: PRF-3 118 a second, PRF-5 a median of 77 ms, PRF-6 120 frames a second everywhere.
- **The first try at the final run failed:** the app wrote no measurement. Nevada saw that the app's window showed Edge's "localhost refused to connect", and told Claude Code.
  - That page means the release build was loading its interface from the development server instead of carrying it inside. The same build had measured correctly half an hour earlier, and why it changed wasn't found.
  - Rebuilding with `npm run tauri -- build --no-bundle` fixed it, and the run went through.
  - If it happens again, look at what last wrote `target/release/seura-photos.exe`.

## Edit files in Nevada's library

- **`check.py` passes all 218 edit files in Nevada's library folders.**
  - 20 have edits, using exposure, white balance, highlights, shadows, contrast, saturation, vignette and red-eye; the rest hold only ratings or tags.
  - None has a rotation, crop, straighten, black and white or sepia yet. Those rest on the format's tests and the reference images (slice 10).

## The Editor in release builds

- **The Editor is now in every build:** the Library's and the Viewer's Edit button, E, and the quick fixes. The flag that hid it outside development builds is gone, with the tests for its absence.
- **M1's development-only export stays in development builds.** It writes a Display P3 JPEG without M5's sRGB conversion, sizes or metadata choices. Claude Code asked, and Nevada decided to hide it in 0.3. Its button shows only in development builds, and the command refuses in a release build too.

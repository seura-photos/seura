# Writing edit files from the Library (M3 slice 1)

- **One path for every write from the Library.** `Index::change_shared` in `seura-library` makes a tag or rating change to a selection: it reads each photo's edit file, applies the change, saves atomically, and records what it wrote in the index. It doesn't hold the index's lock while writing, so browsing goes on meanwhile. The Viewer, the Info panel, and the tag picker will all call it through one command, `change_photos`.
- **Seura's own writes don't come back as outside changes.** No separate list of "files Seura just wrote" was needed: the index records the edit file's size and modification time after each write. When the watcher reports the write a moment later, the rescan finds the same size and time and reads nothing again.
- **An edit file with nothing left goes to the Recycle Bin or Trash** (FIL-1). "Nothing left" means no operations, tags, rating, extensions, or fields Seura doesn't know about; the history alone isn't kept. Claude Code chose the `trash` crate (MIT, 5.2.9), which uses the same `windows` and `objc2` versions Seura already has. On the Mac, its default asks Finder to do it through AppleScript, which makes macOS ask the user to let Seura control Finder, so Seura uses Apple's file manager instead. Whether Finder's Put Back works for those files is to be checked on the Mac.
- **Read-only folders are found without writing anything** (TAG-7). On Windows, a folder's read-only attribute means nothing, so Seura opens the folder asking only for the right to add files, and the system checks the permissions. On the Mac, it asks `access()`. A refused save counts as a read-only folder only if the folder itself refuses new files: one read-only edit file doesn't make its folder read-only. The data-safety test makes a folder truly read-only with `icacls` on Windows and with permissions on the Mac.
- **A gap for slice 5 (undo), and Nevada's decision.** An edit file counts as empty however much history it holds, as the edit format's advice implies. So pressing `0` on a photo whose only content was a rating sends the file, and its history, to the Trash, and Ctrl+Z then finds nothing to undo. Undoing a fresh photo's first change has the same problem for redo. Nevada asked whether history counts as content (it doesn't), then whether the choice was data integrity against clutter. Claude Code's answer: it's clutter against complexity, since neither option loses anything. Within a session, the in-memory copy undoes exactly as before; after a restart, the Library has nothing to undo anyway (BRW-11), and the file is in the Trash. There were two options: keep files that still have history, which is simple but leaves history-only files beside photos, or have the Library's undo keep, in memory, any file it sent to the Trash for the 10 actions it remembers, and write it back on undo or redo with the record marked. Claude Code recommended the second; Nevada chose it (2026-10-26).
- **Checked on the Mac** by the Mac Claude session, with Nevada watching. Moving a file to the real Trash shows no permission prompt, and Finder offers Put Back for it. The session also caught a test that compared a /var path with the index's /private/var; the behaviour was right, and the test now compares real paths. It also found a HEIC colour test failing on Nevada's Mac but not on CI's Mac runners, from before this slice (#91).

# Outline stars, and drives with no Recycle Bin (M3 slice 11d)

- **Empty stars are outlines** in `ratingOff`, and filled ones are solid in `rating`, so they differ by shape as well as colour (visual design, "Stars"; design answers, 2026-10-27). In a read-only folder both are in `ratingDisabled`, which replaces the half-transparent stars. A line of text already says why (TAG-7).
- **Drives with no Recycle Bin are left out of Delete** (BRW-9, as the design session decided). On Windows, only fixed drives have one. On a USB stick or a network share, Windows deletes for good instead, which would break CLAUDE.md's rule 5. Seura now asks the system for the drive's type before calling the Recycle Bin, once per folder. The confirmation says which photos are left and why, as it does for read-only folders. A drive whose type the system doesn't report counts as having no Recycle Bin.
- **The Mac needs no such check:** there, the system call refuses where there's no Trash, and never deletes permanently. Measuring a network volume on the Mac is still to do.
- **Windows doesn't ask, it deletes (#115).** Nevada tried Delete on a photo on a USB stick, on a branch without this check, as in 0.2.0. It was deleted for good, with no prompt and not in the Recycle Bin. Explorer asks first for the same file. Slice 9's journal said Windows would ask, because the `trash` crate requests the warning (`FOF_WANTNUKEWARNING`). But it also turns all prompts off (`FOF_NO_UI`), and that wins. It was never measured on such a drive. So the refusal is now in Seura's one Trash function, before calling the system, and every file goes through it: Delete, an edit file with nothing left (FIL-1), and Start over's fallback (FIL-4). On a stick, those now fail and leave the file where it is. Claude Code's mistake, caught by Nevada's test.
- **Decided (decision 0017, #116):** Nevada proposed deleting an emptied edit file directly on such drives. The design session agreed, with conditions, and added Start over. It turned down a "Delete anyway" for photos and importing from cards, and gave the confirmation's wording; Nevada concurred.
- **Built as decided:**
  - **FIL-1:** on a drive with no Trash, an edit file with nothing left is deleted directly. Read again just before, the file on disk still holds the rating being cleared, so Claude Code saves the emptied document first, reads it back, and deletes it only if it's exactly those bytes and holds nothing. If anything differs, the file stays and holds nothing. A file with another app's extension is never deleted. Undo writes a new file with the cleared rating (tested).
  - **FIL-4:** Start over copies the file to Seura's folder, reads the copy back, and deletes the original only if they match byte for byte. Otherwise it removes its own copy and stops (tested both ways).
  - **The Trash's refusal is now a type of its own** (`seura_edit::NoTrash`), so only that refusal leads to a direct deletion, and any other failure doesn't.
  - **A new data-safety test lists every direct deletion** in the app's code with why it's allowed, so a new one fails until it's reviewed. Besides decision 0017's three, it lists Start over removing its own copy when it fails, and the thumbnail cache, which is Seura's own data and rebuilt from the photos.
- **On the Mac, nothing changes yet:** the system refuses where there's no Trash, which isn't the `NoTrash` refusal. So on a Mac network share, clearing a rating fails, and Delete reports a failure, until network volumes are measured.
- **Checked on Nevada's stick without changing it:** `trash_check` now says whether a file's drive has a Recycle Bin. `E:` (FAT32, removable) has none, and the fixed drives do.
- **Nevada checked it on a USB stick, on main after #113 merged** (2026-10-27):
  - Delete leaves the photo where it is, with the new message.
  - When a rating is cleared, or the rating itself is undone with Ctrl+Z, the edit file is deleted.
  - Ctrl+Z after clearing the rating writes the file again.

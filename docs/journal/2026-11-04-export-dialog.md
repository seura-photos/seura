# The Export dialog and batches (M5 slice 4)

- **Export has screens now.** The dialog follows the wireframe, Export is on the Library, Viewer and Editor toolbars, Ctrl+E works everywhere (Cmd+E through the File menu on the Mac), and M1's development-only export is gone.
- **The core keeps the folder (Claude Code's choice).** The UI asks for the system's folder dialog and only shows what comes back; it never sends a path to write to. That's how the Welcome screen already treats folders.
- **The dialog's first state differs from the mockup in one way (Claude Code's choice).** The wireframe shows "Long edge 2048" selected, but nothing in the spec says that's the default, and its path isn't the spec's first folder either, so Claude Code treated those as example values. The first export is at the original size, since a photo smaller than expected is the worse surprise. "Include tags and rating" starts on, as drawn. Both are one line to change, and they're raised with Nevada in the pull request.
- **Exports stay apart from Enhance's downloads.** Each has its own Stop, so canceling an export doesn't stop an Enhance. One export runs at a time; asking for another says one is still running.
- **Photos on the computer go first,** as in Enhance, so a slow download holds nothing else up and canceling keeps the most.
- **A photo whose edit file can't be read isn't exported (Claude Code's choice).** Exporting it without its edits would look like a finished file and be wrong. It's reported with the reason, and the others go on.
- **A full drive or a folder that can't be written stops the batch,** and says how many were left, since every later photo would fail too. One unreadable photo is reported and the rest continue, as the plan says.
- **The tests caught a formatting surprise:** Fluent writes numbers for the reader's region, so "Long edge 2048 px" came out as "2,048". It's now passed as text. The dialog's Tab key also only went round buttons, since no dialog had fields before; it now includes fields, and stops once at a group of radio buttons.
- **How far it's been checked:** in the real app on Windows, Claude Code opened the dialog and exported one photo with a generated library, driving it through UI Automation; Windows read the file's details and the original's checksum didn't change. UI Automation can't select several photos, so batches, Cancel, and the cloud are covered by tests only until Nevada runs the plan's "done when".
- **On the Mac,** the Mac session ran the tests, which passed, and drove the app through the accessibility API, with Accessibility turned on by Nevada. File > Export… is off with nothing selected and on with a photo selected, its shortcut is Cmd+E, and it opens the dialog. The export wrote the file and left the original's checksum unchanged.
- **A bug the tests had missed, found there:** exports could be read only by their owner (`-rw-------`), because a temporary file starts that way and the rename keeps it. On a shared folder, or for another account, the export looked unreadable. This had been true since M1. The Mac session found it by comparing the export's mode with the original's; Claude Code fixed it, so an export now gets whatever any new file gets, with a test. Windows doesn't have these modes.
- **Nevada's first run of the "done when" found a moving button.** Nevada ran the first nine manual tests, covering a batch, Cancel and cloud photos. The originals didn't change, and this was the one problem they noticed. But during a batch with cloud photos, the progress message widened and narrowed with its text, and since it's centered, Cancel moved and was hard to click. Tests can't see that. The message now keeps one width with the button at its right edge, and long names are cut short. The count moved ahead of the name so it's never the part cut off, and progress sits below any other message so one going away doesn't move it. Enhance's progress and Stop got the same treatment. Nevada asked for this bug to go in the next devlog post.
- **Both machines passed the first nine manual tests.** Nevada ran them on Windows, then on the Mac, and the moving button looked fixed.
- **Exporting again makes copies, and now it says so (Nevada's suggestion).** Export never replaces a file, which Nevada agrees with, but rerunning a batch after something like a dropped connection would quietly give the photos that had already worked a second copy. Nevada asked for this in the documentation and suggested the end of the export say so. The summary now counts how many got a number, one photo's message says so too, and the M7 user guide's line covers it.
- **Not done:** the plan says `scripts/app_data_audit.py` should run over a build that has exported. The script only launches and quits, and driving an export from it needs a way in that doesn't exist yet.

# The HEIC colour test on Nevada's Mac (M4 slice 0; #91)

- **The Mac session found the cause** by bisecting 265 commits: 6fb8ea2 (M1 slice 5a, the working-space decode). From then on, every HEIC was drawn into an 8-bit Display P3 bitmap and converted back to sRGB by moxcms. An sRGB HEIC went sRGB → P3 → 8 bits → sRGB. For a saturated colour, a dark channel sits where sRGB's curve is steepest, and one 8-bit step in P3 red moved sRGB red by about 10 levels. The test's green corner read [8, 253, 2] against a tolerance of 4.
- **Why CI passed:** whether P3 red rounds down or up depends on hundredths of a level in the decoder's output. Real Apple processors decode HEVC in hardware, while CI's virtual machines probably don't, and CI's output happened to round the lucky way. iPhone photos, which carry a Display P3 profile, weren't affected. The loss also reached the Editor and export for sRGB HEICs, not just thumbnails.
- **The fix, the Mac session's recommendation, built by Claude Code:** draw in the image's own RGB colour space and carry its profile, so moxcms makes the one conversion. Display P3 remains the fallback when the space has no profile moxcms can read. The session advised against widening the tolerance, which would hide real colour-management errors in dark channels.
- **Checked on the Mac by the Mac session:** clippy is clean, the #91 test passes (green [2, 253, 2]), the P3 fixture keeps its wide colour, and moxcms reads both of Apple's profiles (sRGB, 3,144 bytes; Display P3, 536 bytes). The check that the profile is readable was added afterwards, at the session's suggestion. CI's macOS runners compile it.

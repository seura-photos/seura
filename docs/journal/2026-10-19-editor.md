# 2026-10-19: The first edit, end to end (M1 slice 5b)

The Editor's walking skeleton: double-click a photo, drag the exposure slider, and the preview follows; the change is saved beside the photo; Export writes a JPEG.

## How it fits together

- **One shader, three hosts:** the same WGSL runs in wgpu for export, in WebGPU for the preview, and, translated by naga, in WebGL2 where the web view has no WebGPU. Only the last step differs: the preview is encoded for Display P3 and the web view maps it to the screen, while export is encoded for sRGB.
- **The photo arrives already decoded:** the core decodes it to fit the window at the screen's density, in the working space, and the preview fetches the half-float pixels over the `seura://` protocol. The UI never reads the photo itself (decision 0009).
- **Saving:** the preview follows every move of the slider; the edit file is written when the slider rests for 0.3 seconds, so each pause is one entry in the history, and the change is on disk well within EDT-11's one second. Opening a photo writes nothing; the edit file appears with the first change.
- An edit file that exists but can't be read is shown as a message, and the slider is disabled: it's never overwritten (rule 4).

## The render check

As Nevada and Claude agreed for slice 5a, the parity test runs in the real web views rather than a separate browser. `SEURA_RENDER_CHECK=1` starts the app in a mode that renders a reference image with every preview path the web view has, sends the pixels to the core, compares them with wgpu's export render, and exits with the result. CI runs it on Windows, macOS 26, and macOS 15.

- On Nevada's PC, WebView2's WebGPU and WebGL2 both match export **exactly** (largest difference 0 out of 255).
- Claude broke the WebGL2 path on purpose (leaving out the row flip that WebGL's bottom-up readback needs): the check failed with a difference of 255, as it should. The autosave test was checked the same way, by making it save on every move.
- The edit file the Editor writes passes the format repository's `tools/check.py`.

## Small things

- WebGL reads pixels bottom row first, and WebGPU pads rows to 256 bytes when copying them out; both are handled where the pixels are read, and the check would catch either going wrong.
- TypeScript's DOM types include WebGPU's interfaces but not its flag constants, so the few values needed are written out from the specification rather than adding a types package.

# Why CI got slower, and why it didn't need fixing

- **Nevada noticed** CI taking longer than it used to and wondered whether the code's growing complexity was to blame.
- **Claude Code measured it** across the last 40 runs: most build jobs took 3 to 7 minutes, but some took 15 to 36. The long ones were the runs where `Cargo.toml` or `Cargo.lock` had changed (a new crate, or the change that optimizes libraries in development builds), which invalidates CI's cache of compiled dependencies, so everything was compiled from scratch. The development-build change made those cold builds slower still, since optimized compiling takes longer.
- **Claude offered** to make CI's tests compile dependencies unoptimized again, but suggested waiting for a run with an unchanged lock file first. The next such run (slice 7b) took 6 to 7 minutes, so nothing was changed: growth in the code adds a little, but the cache is what matters.

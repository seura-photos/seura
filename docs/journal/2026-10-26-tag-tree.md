# The tag tree (M3 slice 4)

- **TAGS in the sidebar, below FOLDERS,** with its own heading kept in view as the list scrolls, as the wireframes have it. `family/kids` shows as `kids` under `family`, each level sorted by name.
- **Counts follow TAG-5 and the design session's answer:** a node shows how many photos have exactly that tag. A node no photo has exactly, such as `family` when only `family/kids` is used, shows no count, not 0 and not a total. Selecting one shows a line saying so, and that its photos are under the tags beneath it.
- **Selecting a tag shows its photos from every folder**, in the app's sort order. It replaces the selected folder: the heading shows the full tag ("2 photos, from every folder"), and the Viewer's Esc goes back to the tag. A tag no photo has any more leaves the tree, and the grid, the next time the library changes (TAG-4).
- **Built like the folder tree:** the same ARIA tree keyboard (arrows open, close, and move; Home and End), and nodes start open and stay as the user leaves them for the session. Whether nodes should start closed in a large tag list is left for Nevada to judge with his own tags.
- **Nevada's two findings while trying the branch:**
  - **Both trees now start closed.** In M2, library folders opened themselves at launch, and with his OneDrive's many subfolders the sidebar scrolled straight away. Nevada proposed showing only the top level at launch, for folders and for tags; Claude Code agreed. What the user opens stays open for the session. This changes M2's behaviour, by Nevada's decision.
  - **The TAGS heading didn't fully cover FOLDERS'** when scrolled to the top: both stuck at the same place, but FOLDERS' heading is taller (its + button, and the notice under it). Each heading now sticks only within its own section, so FOLDERS' scrolls away as its section ends and TAGS' takes its place, as in Finder's and Outlook's sidebars. Both headings are now the same height, whether or not they have a + button.
- **Checked by Nevada on his library:** both trees open at their top level, and scrolling, TAGS' heading pushes FOLDERS' off the top. He'd wondered whether both headings should stay, stacked; he prefers it as built, since once only tags are in view a FOLDERS heading labels nothing, and two stacked headings would cost a row's height on a small window.
- **The selected row was too faint** (Nevada, in the screenshots): `accentSubtle` on the sidebar is about 1.1:1 in light mode and 1.4:1 in dark, below the 3:1 that guidelines ask for anything showing a state (WCAG 1.4.11), so the selection showed mostly as slightly bolder text. Claude Code added, from the design's own tokens, a 3-pixel accent bar on the row's left edge and accent-coloured text and icon, keeping the fill, as Explorer and many sidebars do. It applies to both trees, so it's for the design session to confirm. The bar follows the row's rounded corners.
- **A count slipped through** for a node no photo has exactly: the heading said "0 photos, from every folder" and the status bar "0 photos", against TAG-5's "no count, not 0". Both are left out now; the message in the grid's place explains. Found in the same screenshots.
- **The screenshots** were taken as before, with Nevada clicking in a development build on the generated test library. He removed `family` from two photos first, so the tree showed both kinds of node.

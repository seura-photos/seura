# M3 wrap-up (slice 11)

- **Every edit file Seura wrote in Nevada's library passes the edit format's `check.py`** (the submodule's version, 43dd744), on both machines. On Windows, 12 files: two more were cloud-only and were skipped rather than downloaded. On the Mac, 15 files, none cloud-only. Between them they have tags, ratings, history, an exposure edit and an operation Seura doesn't know (`com.example.toneCurve`), kept as written. The check only read the files.
- **The Mac had no `jsonschema` for `check.py`.** Nevada agreed to a throwaway virtual environment, deleted afterwards. macOS's own Python is 3.9, too old for jsonschema 4.26.0, the version Windows has. So the Mac session built the environment from Homebrew's Python 3.13 instead, which leaves Homebrew's Python itself unchanged, and it suggested doing so.
- **Search is now measured in the app (FND-3).** The measurement script types `img_01234` into the search box a letter at a time and times each letter until its results are drawn, on the large library. `--small`'s large library grows from 5,000 to FND-3's 10,000 photos for it. The first run quietly reused the old 5,000-photo library, because its folder's name didn't change with its size; it's now named by its size. The first search text, `img_12345`, matched nothing in a 10,000-photo library, so it changed too.
- **FND-3 was met at 10,000 photos (68 ms, slowest letter), but 50,000 found a slow path.** There, the first letters match every photo and took about 430 ms on Windows and 204 ms on the Mac. The time followed the number of results, not the library. The index's own search took under 2 ms; timing the command apart from the grid showed the UI's drawing adds almost nothing. Temporary timings inside the command, not committed, found the rest: about 125 ms sorting, 70 ms making thumbnail jobs, and about 90 ms sending 8 MB of results to the web view.
- **Two causes, both small fixes (Claude Code).** The sort compared names on every comparison, not only to break a tie between equal dates (`then` where `then_with` was meant), and the name comparison built a new string for every run of digits. And each thumbnail's cache key was built from 16 separate small strings. With names compared only for ties, without new strings, and each key written into one string, the core's part for 50,000 results fell from about 220 ms to 100 ms on Windows, and for 10,000 from 45 ms to 19 ms. The keys are unchanged, so existing thumbnail caches stay valid.
- **The Mac session pointed out that the table read like a miss** at 50,000 photos, where FND-3 sets 10,000. The goal column now says "at 10,000 photos", and both sizes are measured: `--small` for the spec's size, the full run as a stress test.
- **The Mac session caught two oddities in its second run.** First, the command timed on its own often took longer than the whole letter, up to 779 ms. The cause was in the app: every search queued all its results' thumbnails again, so each letter of a 50,000-photo search sent the UI 50,000 notices about thumbnails already made, and the next command waited behind them. Search no longer queues thumbnails (Claude Code). Every scan already queues the whole library, and the grid asks for the ones on screen. Folders and tags still queue theirs, once per click. Second, one run took 333 s to fill a grid; the Mac session suggested the display had slept, which stops WebKit drawing frames. On macOS the measurement now keeps the display awake with `caffeinate` while it runs.
- **With the three fixes, search is within 200 ms even at 50,000 photos:** at FND-3's 10,000, the slowest letter took 46 ms on Windows and 79 ms on the Mac; at 50,000, 142 ms and 119 ms. Every browsing target is still met on both machines, with times about as in M2. The memory peaks are higher, because the search step is new, and macOS gives only the peak. The Mac session also pointed out that 1,000 12-megapixel photos, through the Viewer, peaked at 608 MB on the Mac (284 MB on Windows): within PRF-7, but worth remembering for M4's Editor. All in `docs/benchmarks/m3-search.md`.
- **Main's CI failed once after #105 merged (Nevada spotted it):** a UI test on the `macos-latest` runner only. The App tests' stand-in for the selection summary lacked `partialTags`, which the real command always returns. The Info panel asks for it only once a selection settles, so only a slow runner reached it before the test ended. Fixed in its own PR (#106), so main didn't wait for this slice.

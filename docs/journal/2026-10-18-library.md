# 2026-10-18: Library scan, index, and benchmarks (M1 slice 3)

Claude built `seura-library` on branch `m1/library`: library folders, scanning, the in-memory index and its snapshot, fingerprints, and the benchmarks that decide whether decision 0010 (an in-memory index rather than SQLite) holds.

## bincode is unmaintained

- The technical design and decision 0010 name `bincode` for the snapshot. Checking crates.io before adding it, Claude found that bincode's developers stopped work permanently in December 2025, after a harassment incident; RustSec published an unmaintained advisory (RUSTSEC-2025-0141), and the project's `cargo-deny` check would reject it.
- Claude chose `postcard` instead: serde-based like the rest of the project, a documented and stable encoding, MIT or Apache-2.0, and one of the alternatives the advisory lists. Decision 0010's substance (in memory, one snapshot file) is unchanged; only the encoding library is, so it's recorded as an amendment to 0010 and in the technical design rather than a new decision.

## Choices made while building it

- **Cloud placeholders are never read.** Reading even the first bytes of a OneDrive or iCloud file that's only in the cloud downloads the whole file, so pointing Seura at a synced Pictures folder could have pulled down an entire library during the first scan. The scanner recognizes placeholders (Windows file attributes, macOS's "dataless" flag) and trusts their extension instead of checking their signature. Thumbnails for them are a question for slice 4.
- **Unchanged photos aren't opened.** A photo with the same size and modification time as in the index is left alone; only new or changed files have their first bytes checked, and an edit file is re-read only when it changes. A rescan of 10,000 unchanged photos takes about 10 ms.
- **Symbolic links are skipped,** since they could lead outside the library or in circles. Folders with no photos anywhere inside them aren't kept in the index.
- **A missing library folder** (a disconnected drive) is reported as unavailable and its photos are kept, the beginning of LIB-6.
- **The snapshot** starts with a marker and a layout version, and is checked for consistency on load: a damaged or outdated file is ignored, which only costs a full re-scan. The cache folder gets a README saying it's safe to delete, as the technical design describes.
- **`seura-edit`'s atomic write is now public,** so the snapshot is written by the same tested code as edit files, rather than a second copy.

## Benchmarks

- Synthetic libraries of 10,000, 50,000, and 100,000 photos, shaped like a family library (dated folders, one 1,000-photo folder, a few hundred tags in a hierarchy, 40% tagged, a third rated, 15% edited), generated in memory. Memory is measured with a counting allocator, so it's exact rather than estimated from the operating system.
- The functional spec's targets cover the whole app, so Claude set budgets for the index's share, recorded in `docs/benchmarks/m1-index.md` for Nevada to accept or change: index memory at 100,000 photos ≤ 100 MB (PRF-7 allows the whole app 1 GB at 50,000); snapshot load at 100,000 ≤ 500 ms (a quarter of PRF-1's 2 seconds); listing a 1,000-photo folder ≤ 10 ms (PRF-2); search per keystroke at 10,000 ≤ 200 ms (FND-3 exactly).
- Everything passes with a wide margin on Nevada's Windows PC, on his MacBook Pro (run by the Claude Code session there), and on both CI runners: at 100,000 photos the index takes 34 MB and loads in 36 to 95 ms, and the slowest search keystroke takes under 8 ms. The in-memory index holds, as decision 0010 hoped, and its estimate of about 30 MB per 100,000 photos was close (measured: 340 bytes per photo).
- The benchmark runs in CI on Windows and macOS and fails the build if a target is missed, so a later change that makes the index slower or larger is caught.

## Mistakes caught

- A search-and-replace in a test file was broader than meant and changed calls it shouldn't have; Claude spotted it in the next check and undid it.
- A scripted edit turned escape sequences in byte strings into real bytes, including NULs; the compiler refused the file, and Claude rewrote the signatures as plain byte arrays.
- Claude pushed the branch and then waited for a CI run that never came: CI runs for pull requests and pushes to `main`, and no pull request had been opened. The wait didn't check whether a run existed, so it would have waited forever; Nevada asked whether anything was still running, which surfaced it. Waits for CI now check for a missing run and give up after 30 minutes.
- As before, Claude checked that the new safety test can fail: making the scanner open photos for writing made it fail, because the stand-in photos are read-only.

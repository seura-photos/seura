# Crop mode (slice 5c)

- **The design was settled before any code.** Claude Code listed the behaviours the wireframe and the spec left open, each with a suggestion. The design session confirmed them all in #172 and added six:
  - keyboard resizing, with the box and its corners taking the focus in turn;
  - a drag slides along the turned photo's edge rather than stopping;
  - Landscape and Portrait are off for 1:1 too;
  - Ctrl+Z steps back within crop mode;
  - leaving the photo any other way counts as Done;
  - no Compare while cropping.
  The first set of questions reached the design session cut short on its first paste (journal, `2026-10-29-rotate-flip.md`); this one went in whole.
- **What it does:**
  - `C` or Crop and straighten opens the whole photo at Fit, with the zoom kept to return to. The header becomes "Crop and straighten", and the filmstrip goes.
  - The box shows the outside darkened, the uncovered corners as the dark surround, and the thirds lines.
  - Corners resize, edges resize one side (or both, with a ratio), and the inside moves the box. It slides along the turned photo's edge.
  - The ratio buttons set the largest box of that ratio centered where the box was. The size label shows the photo's own pixels.
  - Straighten goes from −45° to +45° in tenths, a degree with Shift. The box shrinks as the photo turns and grows back toward the box the user set, as the appendix gives it.
  - Done or Enter saves one record, "Crop" or "Straighten"; Esc or Cancel discards. `[` and `]` rotate with the box.
- **The math is in one place, `crop.ts`,** tested on its own and against the appendix's crop-inside vectors. The core rounds the box's edges inward to whole pixels as it saves, so rendering can't show a sliver of corner.
- **Slider gained ranges and Shift steps** for the straighten slider. The light and color sliders now step 10 with Shift too. Claude Code's question to the design session had said "as the other sliders do", which wasn't true of them before. It is now.
- **Caught along the way:**
  - Two of Claude Code's own expectations were wrong, not the code. A box it expected to shrink at 8° fitted without shrinking. A test meant to catch a double save passed without the guard it was for.
  - The second led to a closer look. While cropping, the Editor's own Done and move paths can't be reached, so the double save couldn't happen. The guard stays as insurance; the test went.
  - Leaving while cropping needed handling where the Editor is left from outside (another photo opened, the Editor closed), which now keeps the crop.
- **Nevada tried it (2026-10-30), and found two things:**
  - **Tabbed to a corner, the arrow keys could only make the box larger.** With a ratio locked, which Original is, the corner's new size came from whichever direction made it bigger. A key moves one direction, so a shrink was always overruled by the unchanged one. Now the direction that moved sets the size. Which keys grow or shrink a box still depends on the corner, as it should. Tests now cover shrinking from a corner, and they fail on the old code.
  - **On a straightened photo, the box seemed to stop short of the edge.** Claude Code first took this for a bug in how the box slides, and changed it to keep sliding while it gained anything. A probe across angles and directions showed the change gained nothing anywhere, so it was taken out again. What Nevada saw is the geometry. The box stops when any one corner reaches the photo's slanted edge, which can leave its other side visibly short. With a ratio locked, the corners next to the dragged one move too, and either can reach the slant first.
- **Nevada tried again, and showed the explanation was wrong.** On a straightened photo, a box dragged right stopped where a corner met the slant. Moving the pointer vertically in the same drag didn't let it go further right. Letting go and dragging again did, a step at a time.
  - **The cause:** each drag's position was worked out from where the drag began, across first and then down. Once across was blocked, moving down within that drag couldn't open it again. A new drag started from the new height, which is why steps worked.
  - **Claude Code's probe had missed it** because it tried few starting places. At mid-height the slant doesn't block, so old and new code agreed, and that's where the probe and the first test looked.
  - **The fix:** a dragged box now goes to the place nearest the pointer where it still fits on the turned photo. That's a point of a convex polygon, the region shrunk by the box's size. Against a slanted edge it slides along it, across and down together. Near the top of a photo turned 25°, the old code stopped a box at 3,801 pixels; it now slides to the frame's edge.
  - Corners resizing freeform repeat their across and down moves while that gains anything, for the same reason.
  - The tests reproduce Nevada's case and check that no nearby place that fits is nearer the pointer. Both fail on the old code.

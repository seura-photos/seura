# Filters (M3 slice 6b)

- **The index already filtered** (M1: minimum rating, tags, edited, date taken), so the Rust side is wiring: the grid's three commands (a folder, a tag, search) each take the filter, and one store action fetches what the grid shows through it. Every view change, sort, filter change and library change goes through that one path, so a photo rated below the filter leaves the grid as soon as it's rated.
- **A tag in the filter that no photo has any more matches nothing,** rather than being dropped silently: the chip stays, so the empty grid has its reason on screen, with Clear filters beside it.
- **Only the Filter button's place was designed** (the styled mockup puts it before the sort control). Claude Code chose the rest, to be checked in a design session: Filter opens a row of controls under the heading (Rating as "At least N stars", Tags as a list that adds one at a time, Edits as Any, Edited, or Not edited, and Taken from and to as date fields). The active filters are a row of chips, each with ×, and Clear all, shown whether or not the controls are open. The Filter button takes the accent colour while any filter is set, and the status bar says "3 of 214 photos".
- **Dates taken are clock times with no time zone,** so the date fields are read the same way: the "to" date includes the whole of that day.
- **A possible gap (ACC-6), to check:** the web view probably draws its date fields in the display language's format, not the region's, so on an English Windows set to a German region the field might show 07/12/2026 while the chip says 12.07.2026. The chips follow the region.
- **Search's speed at 10,000 photos (FND-3)** is measured at the wrap-up (slice 11), with the other targets.
- **Nevada found the date filter missing photos,** and suspected the date taken against the file's date, and then cloud photos. Both were right. The index learns a photo's date taken only when Seura decodes it for a thumbnail, so cloud-only photos (never decoded, LIB-9), photos with no date recorded, and photos not decoded yet had none, and the filter left them all out, though the grid sorts them by their file date (BRW-2). The filter now places them by file date too, the same as the sort. The cost: a cloud-only photo is placed by its file date until its date taken is known, which may be when it was synced rather than taken.
- **Found while looking:** a date taken learned during a session is lost if the app is stopped without quitting (Ctrl+C on `cargo tauri dev`, or a crash), and since the thumbnail is then already made, the photo is never decoded again to learn it. Filed as #99 rather than fixed here, since it affects sorting as much as filters.
- **The date pickers are the web view's own,** so they differ by platform: Edge's calendar on Windows, WebKit's macOS-style picker on the Mac. Nevada noticed the difference and decided to keep them, rather than build a custom picker; their look and the format question above go to a design session with the rest of the filter controls.
